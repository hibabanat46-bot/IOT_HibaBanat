## FreeRTOS Queue Communication on ESP32

### Project Overview

This project demonstrates task-to-task communication using **FreeRTOS Queues** on an ESP32.

The project is based on Task 3.6, where sensor data was shared between tasks using global variables. In Task 3.7, the shared global variables were replaced with a **FreeRTOS Queue** to provide safer and more structured communication between the Sensor Task and Output Task.

---

## Objectives

* Replace shared global variables with a FreeRTOS Queue.
* Implement structured sensor messages.
* Use `xQueueSend()` for sending sensor data.
* Use `xQueueReceive()` for receiving sensor data.
* Implement blocking communication between tasks.
* Test Queue Depth = 1 and Queue Depth = 5.
* Observe Queue overflow and dropped messages.
* Analyze stale data and FIFO behavior.
* Verify that the Queue solves the race condition from Task 3.6.

## Software Architecture

The application contains two FreeRTOS tasks:

### 1. Sensor Task

The Sensor Task:

1. Reads the IR sensor.
2. Reads the potentiometer using ADC.
3. Stores both values in a `sensor_message_t` structure.
4. Sends the structure to the FreeRTOS Queue.
5. Repeats every 100 ms.

```c
typedef struct
{
    int pot_value;
    int ir_state;
} sensor_message_t;
```

### 2. Output Task

The Output Task:

1. Waits for a message using `xQueueReceive()`.
2. Reads the potentiometer and IR values from the received message.
3. Converts the potentiometer value into a PWM duty cycle.
4. Controls LED1 using PWM.
5. Controls LED2 according to the IR sensor state.
6. Logs the received data.

---

## FreeRTOS Queue

The Queue is created using:

```c
sensor_queue = xQueueCreate(
    5,
    sizeof(sensor_message_t)
);
```

The Queue was tested with two different depths:

* **Depth = 1**
* **Depth = 5**

The Sensor Task sends data every **100 ms**, while the Output Task processes data approximately every **500 ms**.

This intentionally makes the producer faster than the consumer to demonstrate Queue overflow.

---

## Queue Sending

Sensor data is sent using:

```c
xQueueSend(
    sensor_queue,
    &sensor_data,
    0
);
```

The timeout is set to `0`.

Therefore, if the Queue is full, the Sensor Task does not wait. The new message is rejected and logged as:

```text
QUEUE FULL - DATA DROPPED
```

The existing messages in the Queue are not overwritten.

---

## Queue Receiving

The Output Task uses:

```c
xQueueReceive(
    sensor_queue,
    &received_data,
    pdMS_TO_TICKS(500)
);
```

The task blocks while waiting for new data.

This means the Output Task does not continuously poll the Queue. It wakes up when a message becomes available or when the 500 ms timeout expires.

# Testing

## Queue Depth = 1

With Queue Depth = 1, only one message can wait in the Queue.

Example:

```text
OUTPUT_TASK: RECEIVE: POT = 1599 | IR = 1 | PWM Duty = 99
SENSOR_TASK: SEND: IR = 1 | POT = 1590
SENSOR_TASK: QUEUE FULL - DATA DROPPED: IR = 1 | POT = 1587
SENSOR_TASK: QUEUE FULL - DATA DROPPED: IR = 1 | POT = 1597
```

### Result

The Queue filled quickly because the Sensor Task produced data faster than the Output Task consumed it.

---

## Queue Depth = 5

With Queue Depth = 5, the Queue can store up to five messages.

During testing, different potentiometer values were observed:

```text
POT = 820
POT = 881
POT = 2475
POT = 3767
POT = 3901
POT = 4095
```

The Output Task received older values after they had already been generated by the Sensor Task.

Example:

```text
OUTPUT_TASK: RECEIVE: POT = 820 | IR = 1 | PWM Duty = 51
OUTPUT_TASK: RECEIVE: POT = 881 | IR = 1 | PWM Duty = 54
OUTPUT_TASK: RECEIVE: POT = 2475 | IR = 1 | PWM Duty = 154
OUTPUT_TASK: RECEIVE: POT = 3767 | IR = 1 | PWM Duty = 234
```

### Result

Queue Depth = 5 provided more buffering capacity than Depth = 1.

However, because the Sensor Task was still faster than the Output Task, the Queue eventually became full and messages were dropped.

---

# Queue Depth Comparison

| Feature                       | Depth 1         | Depth 5              |
| ----------------------------- | --------------- | -------------------- |
| Buffer Capacity               | 1 message       | 5 messages           |
| Overflow                      | Happens quickly | Happens later        |
| Temporary Burst Handling      | Limited         | Better               |
| Historical Data               | Very limited    | More messages stored |
| Prevents Data Loss Completely | No              | No                   |

Increasing the Queue depth provides more buffering, but it does not solve the problem if the producer continuously generates data faster than the consumer processes it.

# Race Condition Solution

In Task 3.6, sensor data was stored in shared global variables:

```c
volatile int pot_value;
volatile int ir_state;
```

Both tasks accessed the same variables.

This could cause a race condition because the Sensor Task could modify the variables while the Output Task was reading them.

In Task 3.7, the global variables were removed.

Instead, the Sensor Task sends a complete message through the Queue:

```text
Sensor Task
     |
     | sensor_message_t
     v
FreeRTOS Queue
     |
     | sensor_message_t
     v
Output Task
```

The Queue copies the message into its internal storage, allowing the two tasks to communicate without directly sharing the same mutable variables.

Therefore, the Queue solves the specific shared-data race condition identified in Task 3.6.

---

# Stale Data

A Queue can contain older sensor readings while newer readings are being generated.

For example, the potentiometer could currently be at 4095 while the Output Task is still processing an older value such as 820 or 2475.

This happens because the Queue follows **FIFO (First In, First Out)** behavior.

Queue stale data is different from the shared-variable problem in Task 3.6:

* **Global variable:** stale or inconsistent data can result from timing and shared-memory access.
* **Queue:** older data is intentionally stored as a separate message waiting to be processed.

# Conclusion

Task successfully implemented FreeRTOS Queue communication between the Sensor Task and Output Task.

The shared global variables from Task were removed and replaced with structured messages transferred through a Queue.

Testing with Queue Depth = 1 demonstrated rapid Queue overflow, while Queue Depth = 5 provided better buffering and allowed multiple sensor messages to wait for processing.

The tests also demonstrated FIFO behavior, dropped messages when the Queue was full, and the presence of historical sensor data.

Overall, the implementation demonstrated how FreeRTOS Queues can provide safer task-to-task communication while also highlighting the importance of Queue sizing and choosing an appropriate data-handling strategy for the application.
